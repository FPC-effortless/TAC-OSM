## Why this, and the invalid comparisons it prevents

The previously trained **UCI374** TAC/GRU forecasting result is single-household, repeated DEV, real and replayable but **near-tied** at similar ~103k parameters (GRU 37.668Wh vs TAC 37.932Wh 60-min DEV MAE; not matched in FLOPs/tuning). UCI's broad scalar `Appliances` energy measurement and UK-DALE individual plug wattage **are not the same measured target**, so simply running original models on UK-DALE or comparing their numeric MAE is invalid. The correct study must train both original-architecture descendants anew on the exact same UK-DALE measured kettle channel task under fair source/param/data/tuning/compute, with a held-out new house; do not report UCI374 transfer from this source gate.

Original author metadata reveals **one individual kettle meter** each in House 2 (meter 8), House 3 (meter 2), House 5 (meter 18). Crucially **House 1 meter 10** includes a kettle *plus food processor and sandwich maker* and **House 4 meter 3** includes kettle *plus radio*: these cannot be used as unambiguous kettle-only targets. Rather than selecting favorable houses from model scores, these meter identities are frozen from the publisher's original device mappings, *before* accessing any kettle time-series observations.

**Task definition**: original reported active plug power samples in watts, *not whole-house mains apparent VA*. Each qualifying 10-minute fixed UTC bucket yields arithmetic mean of actual *logged* 6-second samples, provided >=90 non-duplicate source records, first/last sample within 15s of bucket edges, and no internal sample gap over 15s. No interpolation across missing observations, no 6-second power integration falsely presented as ground-truth Wh; minutes/day phase must be derived from original absolute UNIX UTC timestamp (do not reuse UCI row offset). A future prediction would estimate logged sample mean **six 10-minute buckets ahead** (60-minute lead), with an identical observed input history (e.g., past 48 valid contiguous 10-minute buckets) for TAC and GRU. Empty/no-activity windows and active kettle events both counted; report active event selection *in addition to* full-population proper scores so abundant near-zero windows do not disguise missed activations.

**Important sensor caveat:** The published 6s records timestamp the *collector/logged data*, not necessarily the instant the appliance physically measured power nor its availability to a remote service. The [peer-reviewed UK-DALE methods](https://www.nature.com/articles/sdata20157) explicitly say a polled plug may send power data a few seconds old, and an RF receiver can miss/corrupt packets. Logged-sample power is therefore a retrospective source-proxy task; neither causal real-time `available_at` nor physically time-integrated Wh can be claimed merely from a `.dat` line. Publisher metadata marks channels as *preprocessed clipped at 4000 W*. Claims about unclipped raw physical truth are not allowed.

## Admission implementation and security

`specialist_models/model01_ukdale_kettle_source_admission.py` verifies all five original **small** source metadata YAML files from a pinned author commit, source DOI/licence, expected unshared active plug identities and role partition. It reports only source hashes/metadata and NEVER downloads publisher archive/channel data during the metadata audit. A separate strictly opt-in local original meter reader (House 2/3 only) accepts only an exact `house_N/channel_M.dat` path and caller supplied SHA256, checks ascending UNIX seconds, nonnegative integer clipping units, missing/duplicate/gap conditions, and yields observed-only 10-min bucket metadata. It rejects House 5 outright. A supplied hash establishes file byte integrity relative to supplied manifest, **not independent publisher authenticity**; require publisher archive checksum and lawful data provenance before scientific training. Source qualifying code never fits a model, accesses a protected TEST, or silently calls a success gate when samples are absent.
