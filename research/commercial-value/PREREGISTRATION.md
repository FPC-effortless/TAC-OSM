Date: 2026-10-30. First execution status: NOT RUN at registration. This document is committed before PR creation triggers source evaluation. Evidence never implies revenue.

## The buyer problem
Offline Python code editing: predict the next characters while respecting privacy and retaining all computation on the user's device. This study does NOT run on Android and does NOT claim real developer acceptance. The core question is whether original compact 100K TAC has better exact 6-byte suggestion utility than a strong cheap count reference. It is a feasibility screen for the language TAC family, not a direct validation of the recommended 500K LANGLAYER040 architecture.

## Fixed measurement
1. Process observed source byte t chronologically; predict original byte t+1 with no future source access; carry state for each source separately.
2. Score t from 128 through 639 inclusive. Exactly 512 distinct next-byte targets per source, or 1536 targets per model; no document or seed repetition masquerades as independent text sources.
3. At t=128,144,...624 issue exactly one greedy six-byte suggestion produced by consuming only the model's own generated bytes after its original observed prefix. Exactly 32 offers per document, 96/model.
4. Count exact six-byte match. For an optimistic ceiling assume a perfect user knows which offers are correct, accepts them with one Tab, never accepts incorrect suggestions, and experiences zero distraction. Each accepted suggestion saves at most 5 keys. Report exact6 count and simulated keys saved. This is NOT actual user behavior, RoCC or measured time saving.
5. Report per-owner NLL, top1/top5, host CPU step p50/p95 and persistent-state bytes. No energy, mobile speed or realistic SDK RAM claim.
6. FIT-only P3 control uses observed 3-byte context, original FIT-only conditional frequency counts, add-one unigram prior and fixed tau=4 mixture; no training on Flask. P3 has non-matched table memory. A no-completion policy saves exactly zero keys.

## Binding decision rule
TAC is eligible for a separate human/mobile pilot only if original TAC's five-seed mean simulated net keys saved STRICTLY exceeds BOTH the zero-suggestion control and FIT-only P3 on these three owners. Report all five seeds and owners, no best-seed cherry-picking. NLL/accuracy and cost are secondary mandatory reports, not substitutes for the utility gate. Do not claim architecture superiority without full FLOP parity. Negative or zero outcome means FAIL/STOP for TAC-alone autocomplete in this job; a separate preregistration would be needed to investigate hybrid methods.

Even a positive surrogate result cannot demonstrate commercial value. Commercial evidence requires physical on-device exact model export and CPU/RAM/energy parity; direct developer acceptance/time-saved study with distraction costs, and a genuine paid pilot with measured margin. No revenue, paid contract, training, devices or customer claims from this CI study. Preserve original checkpoints; do not merge automatically.
